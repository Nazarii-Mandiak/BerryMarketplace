# 0010. Semantic listing search with pgvector and a shared local embedding library

Date: 2026-07-28
Status: Accepted

## Context

Phase 3 of the "AI Engineer Showcase" plan adds semantic search: a buyer typing "sweet berries for jam" should find a listing titled "ripe strawberry pints" even though the words don't overlap. Keyword search on `Listings` alone can't do that; it needs a vector similarity search over an embedding of each listing's text, compared against an embedding of the buyer's query. That requires answering three questions at once: where the vectors live, what produces them, and where the two production write paths (the AI worker at index time, Task 12; the API at query time, Task 13) get an embedder that produces *comparable* vectors — the same model, the same normalization, the same dimensionality — without duplicating that logic or silently drifting apart.

ADR-0002 already committed Berry Exchange to PostgreSQL for its transactional guarantees, and ADR-0008 anticipated this exact task, choosing the `pgvector/pgvector:pg16` compose image specifically so a vector-search feature wouldn't force a disruptive base-image swap later. ADR-0009 established the shared-library pattern for cross-process code that must stay identical on both sides of a process boundary (`BerryExchange.Contracts` for event schemas, referenced by both API and worker) — this task follows the same shape for embedding logic.

## Decision

Store listing embeddings as a `vector(384)` column on the existing `Listings` table in the existing PostgreSQL database, using the `pgvector` extension, indexed with an HNSW index using cosine distance for approximate nearest-neighbor search. No separate vector database is introduced.

The 384-dimensional vectors themselves come from a local ONNX MiniLM-family model (`bge-micro-v2`, via the `SmartComponents.LocalEmbeddings` prerelease package), wrapped in a new shared class library, `BerryExchange.AiCore`, behind an `ITextEmbedder` interface with a single concrete implementation, `LocalTextEmbedder`. `BerryExchange.AiCore` is referenced by both `BerryExchange.Api` (Task 13 embeds the buyer's search query at request time) and `BerryExchange.AiWorker` (Task 12 embeds each new listing's text at index time, on the `listing.created` event already flowing through RabbitMQ per ADR-0009). Both processes construct the same `LocalTextEmbedder`, so index-time and query-time vectors are produced by the identical model and are directly comparable by cosine distance — there's no risk of the API embedding with one model version or provider and the worker with another. The model runs entirely in-process via ONNX Runtime: no network call, no API key, and the ONNX weights are fetched once at build time (via the package's own MSBuild target, from Hugging Face) rather than bundled in the repo or fetched at request time.

Semantic search degrades to the existing keyword search (`ILIKE` / plain SQL match on listing text) whenever the vector path isn't usable — e.g., a listing indexed before this feature shipped and has no embedding yet — rather than returning no results.

## Consequences

Deploying semantic search costs no new infrastructure: `pgvector` runs inside the Postgres container Berry Exchange already operates, with vectors and rows in the same table under the same transactional and backup story as everything else. Because the embedder is local and network-free *at runtime*, embedding a listing or a query costs CPU time and nothing else once the process is up — no per-call cost, no API key to provision or rotate, and no runtime dependency on an external AI-provider outage taking search down. The `ITextEmbedder` abstraction in `BerryExchange.AiCore` means both consumers depend on an interface, not directly on `SmartComponents.LocalEmbeddings`'s API surface — if that prerelease package's API shifts or a swap to a different local model is ever warranted, it's a change inside `LocalTextEmbedder`, not at either call site.

The tradeoffs: `SmartComponents.LocalEmbeddings` is a prerelease NuGet package, so its API isn't yet stable — this ADR accepts that risk for a demo-scale showcase project rather than hand-rolling ONNX Runtime plumbing directly. HNSW is approximate, not exact, nearest-neighbor search — acceptable for a marketplace search box, not for a use case that needs guaranteed-exact ranking. And because the embedding model runs in-process in two different deployables, a future change to embedding dimensionality or model choice must be rolled out to both the API and the worker together (and existing stored vectors backfilled), since a query embedded by a new model against listings still embedded by the old one would silently produce garbage similarity scores rather than an obvious error.

The "no network call" property is a runtime property only, not a build-time one, and that distinction matters in practice, not just in theory: as the Decision section notes, the ONNX weights are fetched from Hugging Face by the `SmartComponents.LocalEmbeddings` package's own MSBuild target the first time a project referencing it is built on a given machine, then cached locally (`~/.nuget/packages/smartcomponents.localembeddings/<version>/.cache/`) for subsequent builds. That means `dotnet restore`/`dotnet build`/`dotnet test` on any machine without a warm cache — a fresh developer laptop, or a CI runner — depends on `huggingface.co` being reachable at build time; if it isn't, the build fails outright, not gracefully. This repo's GitHub Actions backend job (`.github/workflows/ci.yml`) runs on a fresh `ubuntu-latest` runner with no caching step configured for `~/.nuget/packages` (unlike the frontend job, which does cache its npm dependencies), so today every CI run re-downloads the model from Hugging Face from scratch. That's an open, currently-unmitigated risk — a Hugging Face outage or rate limit would fail CI, not just degrade search — and is not something this task closes. A reasonable follow-up (not implemented here) is adding an `actions/cache` step for `~/.nuget/packages` keyed on the lockfile/package versions, the same shape already used for the frontend job's npm cache.

Alternatives considered:
- **A separate vector database** (e.g., Pinecone, Qdrant, Weaviate) — rejected. It would mean running and operating a second stateful service, keeping it in sync with Postgres (a listing's canonical record and its vector living in two systems that can drift), and a second connection/credential to manage — all for a workload (tens to low thousands of listings) that `pgvector` on the existing Postgres handles comfortably. If Berry Exchange's catalog ever grows to a scale where `pgvector`'s HNSW index stops being fast enough, that's a swap-in migration behind the same query interface, not a decision this ADR forecloses.
- **A hosted embeddings API** (e.g., OpenAI's `text-embedding-3-small`) — rejected. Every listing creation and every search query would become a network call with its own latency, cost, and API key to provision and rotate — for a "showcase" project, that's an unnecessary external dependency and a recurring cost tied to marketplace traffic. It's also not available from Anthropic specifically: Anthropic does not offer an embeddings API, so a hosted-API path here would mean introducing a second AI vendor into a project that otherwise uses Claude exclusively, purely for this one feature. A local model run in-process avoids both problems and keeps the AI surface area to one vendor.
- **Bundling the ONNX model file in the repository instead of fetching it at build time** — rejected. It would add a ~17 MB binary asset to source control that has nothing to do with application code and would need to be updated in lockstep with any future model swap; fetching it once via the NuGet package's own build-time MSBuild target (cached locally after the first build) keeps the repository itself model-agnostic.

## Update: 2026-07-28 — schema landed

The `vector(384)` column and its HNSW cosine-distance index described above are now real: migration `AddListingEnrichment` (`backend/src/BerryExchange.Api/Infrastructure/Migrations/20260727221407_AddListingEnrichment.cs`) enables the `vector` Postgres extension and adds `Listings.Embedding` (`vector(384)`) plus `Listings.AiTastingNotes` (`varchar(300)`), with an HNSW index (`IX_Listings_Embedding`, `vector_cosine_ops`) on `Embedding`. The integration test fixture (`ApiTestFixture.cs`) now runs against the `pgvector/pgvector:pg16` image (previously plain `postgres:16-alpine`) so this extension is actually available under test, matching what `docker-compose.yml` has used since ADR-0008.
