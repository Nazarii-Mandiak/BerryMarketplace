# 0012. MCP server exposing marketplace tools over stdio, as a separate process behind the public API

Date: 2026-07-28
Status: Accepted

## Context

Phase 6 adds a Model Context Protocol (MCP) server so that AI coding assistants and agent hosts (Claude Code, Claude Desktop, and similar MCP clients) can search Berry Exchange listings, inspect a listing, check availability, and reserve a quantity by the kilogram — as tools an LLM can call directly, rather than a human driving the browser UI. This is a new kind of consumer for the marketplace: not a browser session with a logged-in human behind it (ADR-0004's cookie auth), and not an internal service reacting to a RabbitMQ event (ADR-0009), but an external process speaking the MCP protocol over stdio to whatever host launched it.

Two architectural questions follow from that: how the MCP server should reach marketplace data, and how it should authenticate for the one tool (`create_reservation`) that mutates state.

On the first question, `BerryExchange.AiCore`/`BerryExchange.AiWorker` (ADR-0009, ADR-0010) already establish the pattern of a separate process that shares the same PostgreSQL database and EF Core model as the API. That shape doesn't fit here: the AI worker is a trusted internal component deployed alongside the API, whereas the MCP server's job is specifically to be driven by an external LLM agent — an actor the API's validation, atomic reservation logic (oversell prevention), and authorization rules exist to constrain. Giving it a direct EF Core/DB connection would mean re-implementing (or, worse, half-implementing) every invariant the API already enforces, and any future change to those invariants would need to be kept in sync in two places.

On the second question, three of the four tools (`search_listings`, `get_listing`, `check_availability`) hit endpoints that require no authentication at all. Only `create_reservation` needs an identity, and there is no notion of "the human on the other end of this MCP session" for the server to authenticate as — the MCP client (e.g. Claude Code) is running as whatever local user invoked it, with no browser cookie or Berry Exchange login of its own.

## Decision

`BerryExchange.McpServer` is a standalone console application (project reference-free of `BerryExchange.Api`/`BerryExchange.Contracts`/the EF Core model) that talks to the marketplace exclusively over its existing public HTTP API — `GET /api/listings/search`, `GET /api/listings/{id}`, `POST /api/accounts/login`, `POST /api/listings/{id}/reservations` — using a plain `HttpClient`. It is built on the official `ModelContextProtocol` C# SDK (`AddMcpServer().WithStdioServerTransport().WithToolsFromAssembly()`), registers a `[McpServerToolType]` class (`MarketplaceTools`) whose four `[McpServerTool]`-attributed static methods are the four marketplace tools, and communicates with its MCP client over stdio — the same transport Claude Code and Claude Desktop use to launch and talk to local MCP servers.

The API remains the single owner of every marketplace invariant. The MCP server does no validation, no oversell prevention, and no authorization logic of its own — it forwards a query or a listing ID and returns whatever JSON (or, for `check_availability`, a one-line derived summary) the API returns. This mirrors ADR-0011's framing for `AnthropicGenerativeAi`: a thin, mechanical translation layer with no business logic of its own.

For `create_reservation`, the MCP server authenticates as a single, fixed marketplace account — a dedicated "reservation account," not any human's identity — configured via `BerryMcp:Email`/`BerryMcp:Password`. `MarketplaceApiClient` logs in once (`POST /api/accounts/login`, which sets an ASP.NET Core Identity auth cookie via `SignInManager`) and reuses the resulting cookie, stored in its `HttpClient`'s `HttpClientHandler.CookieContainer`, for every subsequent reservation call in the process's lifetime — it does not log in again per call. `MarketplaceApiClient` is registered as a singleton in `Program.cs`, so there is exactly one `HttpClient`/cookie jar/login-state for the life of the MCP server process, which is correct for this design: the process represents one configured service account, not multiple per-user identities, so there is nothing to isolate between "sessions" the way a browser would isolate cookies per human user.

Following this codebase's established graceful-degradation pattern — ADR-0009's `NullEventPublisher`, ADR-0010's keyless local embedder, ADR-0011's `DisabledGenerativeAi` — `create_reservation` is inert rather than broken when no reservation account is configured: `CreateReservationAsync` checks for `null` email/password up front and returns a plain-text "Reservations are disabled: no marketplace account is configured for this MCP server" message rather than throwing or calling the API. `search_listings`, `get_listing`, and `check_availability` need no such fallback since they hit unauthenticated endpoints and work regardless of `BerryMcp` configuration.

Because stdio is also the wire protocol between this server and its MCP client, `Program.cs` routes all logging to stderr (`builder.Logging.AddConsole(options => options.LogToStandardErrorThreshold = LogLevel.Trace)`) — stdout is reserved entirely for MCP JSON-RPC frames. A stray `Console.WriteLine` or default-provider log line on stdout would corrupt the protocol stream from the client's point of view.

## Consequences

Because the MCP server is a thin HTTP client of the public API, any invariant the API enforces today (oversell prevention, "can't reserve your own listing," auth checks) automatically applies to MCP-driven reservations with zero duplicated logic — the same guarantee ADR-0011 gets from keeping `AnthropicGenerativeAi` as a translation layer rather than a second implementation of anything. The cost is an extra network hop per tool call (MCP server → API) that a direct DB read wouldn't have; for a handful of tools driven by an interactive LLM session rather than a high-throughput path, that latency is not a concern this task needs to solve for.

The single shared `MarketplaceApiClient`/cookie/login-state per process means every reservation made through one running MCP server instance is attributed to the same configured account, regardless of which human is driving the connected MCP client. That is the intended behavior — this is a marketplace service account, not a per-user credential — but it does mean the MCP server cannot currently answer "reserve this on behalf of user X"; it can only ever act as its one configured account. If a future task needs per-user attribution for MCP-driven reservations, that is a structural gap this design accepts and does not attempt to solve (it would need something like OAuth-based delegated auth from the MCP client, which the current MCP transport and this task's scope don't call for).

The reservation tool's "disabled" path means a marketplace deployed with no `BerryMcp:Email`/`Password` still exposes three fully working read-only tools (search, get, check availability) to any MCP client, with `create_reservation` degrading to an explanatory message instead of an exception — consistent with how `DisabledGenerativeAi`/`NullEventPublisher` keep the rest of the system usable when one piece of optional configuration is absent.

Because the MCP server has no `ProjectReference` to `BerryExchange.Api`, `BerryExchange.Contracts`, or the EF Core model, it can be deployed, versioned, and run entirely independently of the API process (a developer's laptop running `claude mcp add` against a local or hosted marketplace) without needing a database connection string, migrations, or any of the API's other infrastructure — just an API base URL and, optionally, a reservation account.

Alternatives considered:

- **Direct EF Core access to the marketplace database** — rejected. It would require reimplementing the API's validation and atomic reservation logic (or risk drifting from it over time) and would break the moment the schema changes without a corresponding MCP server update; going through the public HTTP API means the MCP server automatically stays correct as the API evolves.
- **Per-user OAuth/delegated auth for `create_reservation`** — rejected for this task. MCP's auth story for stdio-transport local servers doesn't map cleanly onto "a specific logged-in marketplace buyer," and this task's brief scopes the reservation tool to a single configured service account. This is a known limitation (see Consequences), not an oversight, and is left as a candidate for a future task if MCP-driven reservations ever need per-buyer attribution.
- **Require `BerryMcp:Email`/`Password` unconditionally, fail fast if missing** — rejected, for the same reason ADR-0009/0010/0011 reject the equivalent choice: it would make three otherwise-independent, unauthenticated tools (`search_listings`, `get_listing`, `check_availability`) unusable without configuration they don't actually need, just because a fourth tool does.
- **Re-authenticate before every reservation call instead of caching the login cookie** — rejected as unnecessary network overhead. `SignInManager.PasswordSignInAsync(..., isPersistent: true, ...)` issues a cookie meant to be reused; logging in once per process and relying on the `HttpClientHandler`'s cookie container for the rest of the process's lifetime is the straightforward, correct use of that cookie, and is what `MarketplaceApiClientTests` explicitly verifies (`Second reservation must not log in again`).
